# Mini Git Version Control

A minimal version control system built from scratch in Python to understand how Git works under the hood.

I'm implementing the core mechanisms step by step, starting with repository initialization, object storage, and the staging area — without using Git internally.

## Current Progress

### Implemented

- **Repository initialization** — creates a `.mini-git/` directory with repository metadata, object storage, references, `HEAD`, and a staging index.
- **Git object model** — represents objects using a type and byte content.
- **SHA-1 hashing** — generates object IDs from an object's header and content.
- **Serialization and compression** — adds the object header and compresses the serialized data using `zlib`.
- **Deserialization** — decompresses serialized objects and reconstructs their type and content.
- **Blob objects** — stores file contents as blob objects.
- **Object storage** — stores compressed objects using their hashes, organised into directories based on the first two hash characters.
- **File staging** — stages files by storing their blob objects and recording their hashes in the index.
- **Directory staging** — recursively stages files inside directories while skipping `.git` and `.mini-git` metadata.
- **CLI** — supports repository initialization and staging one or more paths.

## Tech Stack

- **Python** — core implementation
- **argparse** — command-line interface
- **pathlib** — filesystem operations
- **hashlib** — SHA-1 object hashing
- **zlib** — object compression

No third-party packages are required.

## Getting Started

### Prerequisites

Python 3.10 or newer.

### Clone the repository

```bash
git clone https://github.com/sulfurcodes/Mini-Git-Version-Control.git
cd Mini-Git-Version-Control
```

### View available commands

```bash
python src/main.py --help
```

## Usage

### Initialize a repository

```bash
python src/main.py init
```

This creates the `.mini-git/` directory and its initial metadata. Running the command again reports that the repository already exists.

### Stage a file

```bash
python src/main.py add src/objects.py
```

The file's contents are stored as a blob object, and its path and object hash are recorded in the staging index.

### Stage multiple files

```bash
python src/main.py add src/main.py src/repository.py
```

### Stage a directory

```bash
python src/main.py add src
```

This recursively stages files within the specified directory, excluding `.git` and `.mini-git` metadata.

## How Object Storage Works

Each object has a type and a content payload.

Before hashing or compression, the implementation constructs an object header:

```text
blob <content-size>\0<file-content>
```

For example, a blob containing `Hello World` has this uncompressed representation:

```text
blob 11\0Hello World
```

The implementation then:

1. Combines the header and content.
2. Computes a SHA-1 hash of the combined bytes.
3. Compresses the serialized object using `zlib`.
4. Stores the compressed object under a path derived from its hash.

The resulting storage layout looks like this:

```text
.mini-git/
└── objects/
    └── ab/
        └── cdef123...
```

The first two characters of the hash determine the directory, while the remaining characters determine the filename.

Because an object's hash depends on its type and content, identical blob contents produce the same object ID.

## The Staging Area

The staging index is currently a JSON file located at `.mini-git/index`.

It maps file paths to their blob hashes:

```json
{
  "src/objects.py": "example-object-hash"
}
```

The hash shown above is illustrative. Actual hashes are generated by the implementation.

This is a simplified staging index, not Git's native binary index format.

## Project Scope

This is an educational project focused on understanding version control internals through implementation.

At the current stage, it supports repository initialization, object creation and storage, and staging files and directories. It does not yet implement commits, tree objects, branch switching, checkout, or file history.

The goal is to build these features incrementally while learning how the underlying pieces fit together.
